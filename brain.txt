ARCHITECTURE DECISION RECORD (MNSE pattern vs traditional ROS2)
================================================================================

The Key Insight: The Robot Is an Adapter
You said it perfectly. If LPU provides a prebuilt robot, then:


MNSE TODAY:                              GRACEMO:
                                         
 Hyprland → events → KERNEL              Robot → events → BRAIN
 Browser  → events → KERNEL              Camera → events → BRAIN  
 VSCode   → events → KERNEL              Voice  → events → BRAIN
                                         
 KERNEL → speak → Kokoro TTS             BRAIN → move_to → Robot
 KERNEL → look  → Servo                  BRAIN → speak   → TTS
 KERNEL → type  → Wayland                BRAIN → look_at → Servos
Same pattern. Different sensors. Different actuators.

The robot is just another adapter that:

Emits events: "obstacle 2m ahead", "person visible", "battery 73%", "reached waypoint"
Receives actions: "navigate to kitchen", "stop", "turn left 90°", "say hello"
What MNSE Actually Is (That Makes It Powerful)
MNSE is NOT just an event logger. It's a real-time awareness system with three loops:


LOOP 1 — PERCEPTION (Real-time, <10ms)
  Adapter emits event → EventBus → InspectorState updates
  "What is happening RIGHT NOW?"
  
LOOP 2 — MEMORY (Background, <100ms)  
  Event → Ledger stores → Graph builds relationships
  "What happened before? What's related?"
LOOP 3 — REACTION (Event-driven, <500ms)
  K behavior matches event pattern → triggers action
  "When X happens, do Y"
  
  Example: 
    on hear "navigate to *" → dispatch navigate_to($1)
    on see "person:mab"     → dispatch speak("Hello Muzammil")
    on feel "obstacle:<1m"  → dispatch emergency_stop()
This three-loop architecture is exactly what an autonomous robot brain needs:

Perception loop: Real-time sensor awareness
Memory loop: Learning from experience
Reaction loop: Autonomous behavior

But Wait — Should It Be MNSE Itself or a New Thing?
Two sub-options:

B1: Fork MNSE → GRACEemo Kernel
Copy MNSE codebase, strip desktop-specific stuff, add robot stuff
Pro: Fastest path, everything works
Con: Now you maintain two codebases that diverge
B2: Make MNSE Pluggable → Robot Mode
Add a "robot" module/profile to MNSE itself
MNSE boots with mode = "robot" in kernel.toml → loads robot adapters instead of desktop adapters
Pro: One codebase, MNSE becomes a "context kernel for anything"
Con: Slightly more complex, but cleaner long-term
B3: Build GraCemo Kernel Fresh (Inspired by MNSE)
New Rust project, borrowing patterns from MNSE but clean-room
Pro: Clean codebase, no MNSE baggage, can cite MNSE as "reference architecture" in the paper
Con: Most work, rebuilds things that already work
IMPORTANT

B2 is the most interesting for your research paper. You can claim: "We extended our existing context kernel (MNSE) to support physical robot embodiment, demonstrating that the same event-driven architecture that handles digital context awareness can handle physical robot awareness."
